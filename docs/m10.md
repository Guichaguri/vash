# M10 — closing the gap between the plan and the code

This milestone fixes no bugs a client has reported and adds no feature a client
has asked for. It exists because an architecture review found seven places where
the code and [plan.md](plan.md) have drifted apart, and drift of that kind is
paid for later at a much worse exchange rate.

Same house style as the plan: decision first, then the reasoning, then what was
rejected.

**The through-line.** Plan §8 claims `vash-core` defines the domain and that the
storage and protocol crates are interchangeable adapters on either side of it.
That is true of VCP and memcached. It stopped being true when RESP arrived, and
the boundary has been eroding since — not because anyone was careless, but
because `Command` was never given the shape Redis needs, so RESP went around it.
Most of what follows is the consequence.

---

## The findings, ranked

| # | Finding | Class | Phase |
|---|---|---|---|
| 1 | `INCR` is atomic over memcached and not over RESP, on the same key | Correctness | 1 ✅ |
| 1b | Four conditional writes read a deadline and then write against it | Correctness | 2a ✅ |
| 2 | RESP composes `Store` calls directly, duplicating metrics and error mapping | Boundary | 2b ✅ |
| 3 | The `Store` trait has one implementor and every consumer names the concrete type | Boundary | 3 |
| 4 | `engine.rs` is 1,454 lines spanning six concerns | Cohesion | 4 |
| 5 | `is_read_only` exists three times with three taxonomies | Safety | 5 |
| 6 | The three `drain_*` functions duplicate a stateful, easy-to-get-wrong pattern | Cohesion | 5 |
| 7 | No latency histograms; no `oldest_reader_age_ms`; no per-command breakdown | Observability | 6 |

Ordering is by dependency, not by severity. Phase 1 settles what the `Store`
surface has to be; phase 2 routes the third dialect through it; phase 3 makes
that surface abstract. Doing 3 before 1 would mean re-typing every use site
twice. Doing 4 before 1 would mean moving code that is about to change.

## Phase 1 — atomic read-modify-write in the storage engine

**Decision: the arithmetic family and `APPEND` become primitives the shard
writer evaluates inside its transaction, replacing the read-then-write pairs
the RESP executor performs today.**

### The defect

`INCR` over memcached decodes to `Command::Incr`, reaches `Store::incr`, and is
executed by `engine::apply_incr` **inside the write transaction**, on the shard's
single writer thread. It is atomic by construction.

`INCR` over RESP calls `store.get` and then `store.set`, with nothing between
them. Two clients incrementing the same counter can lose an update.

That is the same logical operation, against the same key, on the same server,
with different guarantees depending on which port dialect the client happens to
speak. `resp.rs` documents the seam honestly and defers it as a storage-engine
change; this is that change.

Affected: `INCR`, `INCRBY`, `DECR`, `DECRBY`, `INCRBYFLOAT`, `INCREX`, `APPEND`.

### Why this is also faster

Making it correct makes it cheaper, which is not the usual direction:

- **A RESP `INCR` costs two hops today** — a blocking-pool read and then a trip
  through the writer queue — and one after. The read was only ever there to
  fetch a number the writer was about to read again anyway.
- **`APPEND` copies the whole existing value out of the mmap** into a `Bytes`,
  concatenates in the executor, and ships the result back down. Evaluated inside
  the transaction it concatenates from a borrowed mmap slice and never
  materialises the old value in the network tier at all. The win grows with
  value size.
- **The deadline reads disappear.** `KEEPTTL`, and `INCREX` with no expiry
  option, currently call `Store::deadline` first purely to reconstruct a TTL to
  write back. A primitive that keeps the record's existing deadline by *not
  touching it* needs no such read.

So: one hop instead of two, one value copy instead of three, and the lost update
closed. No compatibility surface moves.

### The shape

One primitive, not one per command. The skeleton is identical for all of them —
read the live record, parse its text, compute, re-encode preserving tags and
flags, decide the deadline, write — and only the arithmetic differs.

```rust
// vash-core
pub struct Arithmetic<'a> {
    pub key: Key<'a>,
    pub delta: Delta,        // Counter | Int | Float
    pub bounds: Bounds,
    pub on_bound: OnBound,   // Fail | Skip | Clamp
    pub missing: Missing,    // Fail | CreateAtZero
    pub ttl: TtlChange,      // Keep | Set | SetIfPersistent
}
```

Three knobs carry every dialect's semantics:

- **`Delta`** is the numeric domain. `Counter` is memcached's: unsigned, an
  increment wraps at 64 bits and a decrement floors at zero. `Int` and `Float`
  are Redis's. The domain also decides how stored text is read, because
  "leading zeros are not an integer" is Redis's rule and `trim()` is
  memcached's — that is part of the arithmetic, not of the framing.
- **`OnBound`** is what separates `INCR` from `INCREX`. Plain `INCR` **fails** on
  overflow; `INCREX` without `SATURATE` **skips**, leaving the value alone and
  reporting a zero increment; with `SATURATE` it **clamps**. Three behaviours, so
  three variants — collapsing them to a boolean is what would force a fourth
  code path later.
- **`Missing`** is whether the key is created. Redis creates at zero; memcached
  answers `NOT_FOUND`.

`APPEND` gets its own small method rather than a variant of the above: it is not
arithmetic, it already has a working atomic implementation in
`apply_conditional_set`'s `SetMode::Append` arm, and it needs to return a length
rather than a number. Redis's version differs from memcached's in exactly one
respect — it creates the key when absent — so it is that arm plus a flag.

### `Store` surface

```rust
 fn arithmetic(&self, op: &Arithmetic<'_>) -> Result<Option<Applied>>;
 fn append(&self, key: Key<'_>, suffix: &[u8]) -> Result<u64>;
-fn incr(&self, key: Key<'_>, delta: u64, decrement: bool) -> Result<Option<u64>>;
```

`incr` is removed rather than kept alongside: memcached's counter is
`Arithmetic` with `Delta::Counter`, `Missing::Fail` and `TtlChange::Keep`, and
leaving both would leave two copies of the skeleton — which is the maintenance
problem this phase exists to remove, not to duplicate.

`Applied` carries the new value **and the increment actually applied**, because
after clamping only the store knows how far the value moved, and `INCREX` reports
both.

### Supporting moves

- `parse_int` and `parse_float` move from `vash_proto::resp::command` to
  `vash-core`, re-exported from their old path so no call site changes. They are
  numeric text rules, not framing, and the store now needs the identical rules to
  read a stored counter. One definition is the point: two would drift, and the
  failure would be a counter that a client can write and the server cannot read.
- `engine.rs` gains a private `rewrite` helper for "store a replacement for this
  record, keeping its tag table". `apply_incr`, `apply_touch` and both new
  operations end in the same eight lines today.

### Rejected

- **Locking the key in the network tier.** Reintroduces a lock on a path built
  specifically not to have one, and it would have to be a *distributed* lock the
  moment two connections land on different runtime workers. The writer thread is
  already the serialisation point; use it.
- **A generic `compare_and_swap` primitive and looping in the executor.** Turns
  one queue hop into an unbounded number under contention, and makes the tail
  latency of a hot counter a function of how many clients want it.
- **Widening `Command::Incr` in place.** It is memcached's shape — `u64`,
  wrapping, no create — and every one of those is wrong for Redis. Widening it
  would have made a memcached `incr` pay for options only Redis uses.
- **Keeping the two dialects on separate primitives.** They differ in the
  arithmetic and in nothing else. Two skeletons is how the first one grows a bug
  the second one does not have.

### Exit criteria

Concurrent `INCR` from N connections against one key sums exactly, over both
dialects. `APPEND` on a missing key creates it, on a present one keeps its TTL
and flags. Every existing memcached and Redis compatibility test passes
unchanged, and the differential suite still agrees with real memcached 1.6.45 and
real Redis 7.4.10.

## Phase 2a — the conditional writes ✅ **done**

**Decision: the guard on a conditional write is evaluated inside the transaction
that performs the write, never in the network tier.**

Four commands read something and then wrote against what they had read:
`SET … KEEPTTL`, `SET … GET`, `EXPIRE`/`EXPIREAT` with `NX`/`XX`/`GT`/`LT`, and
`PERSIST`. A different class from phase 1's arithmetic — they write a stale
*deadline* rather than corrupt a value — but the same shape of fix.

Three new store primitives: `Store::store` now reports what it displaced,
`Store::expire` applies a guarded deadline change, and `Store::set_many_if`
carries a batch guard. `Set` grew a `TtlChange` in place of its bare `ttl_secs`,
which is what lets `KEEPTTL` travel to the writer as *keep* rather than as a
number someone read a moment ago.

**The lookup was already there.** `apply_set` has always had to read the record
it replaces, to clear its stale index rows. Resolving `KEEPTTL` and capturing
`SET … GET`'s previous value off that same read costs nothing — one B-tree
descent already being paid for, now serving three purposes instead of one. The
deadline reads those two commands used to make are gone outright.

**`MSETEX NX/XX` is the exception, and it is a non-goal rather than a gap.** Its
guard has to see every key at once; a batch spanning shards is several
transactions. Atomic within a shard, documented in `docs/protocol.md` as plan
§16's standing limit.

**Exit criteria — met.** Every read-then-write command in the Redis dialect is
one storage primitive. `set_with_get_reports_exactly_what_it_displaced` fails
against the old shape (33 of 128 values accounted for) and passes against the new
one.

## Phase 2b — one boundary for three dialects ✅ **done**

**Decision: extend `vash_core::Command` with the variants phases 1 and 2a
created, and route the RESP executor through `dispatch::execute` for everything
that fits.**

Phases 1 and 2a removed the *reason* RESP went around the boundary — every
storage operation it needs now exists as a primitive. This phase collected the
dividend.

`Command` gained `Arithmetic` (replacing the memcached-shaped `Incr`, which both
dialects now share), `Append`, `Deadline`/`Deadlines`, `Expire`, and a batch
guard on `SetMany`. `Reply` gained `Arithmetic`, `Length`, `Deadline`,
`Deadlines`, `Applied` and `Swapped`. The VCP encoder's match is exhaustive, so
every new variant forced a decision there — which was the right pressure: the
Redis-only ones answer `Status::Unsupported` until phase 7 gives them opcodes,
and they are listed rather than caught by a wildcard so that adding an opcode is
a compile error here first.

**The Redis adapter is now a codec.** `state.store` appears in it zero times: it
translates, calls `dispatch::execute`, and renders. Several commands collapse on
the way through — `EXISTS`, `TYPE` and `TTL` are one deadline query, `PERSIST` is
a guarded `EXPIRE` — which is the boundary doing its job, being about storage
operations rather than about command names.

**Error classification carries a cause.** Collapsing `StoreError` onto `Status`
alone would have cost Redis four distinct arithmetic messages that all share
`NotNumeric`, and client libraries match on the text. `dispatch::Failed` carries
the status *and* the originating `CoreError`; memcached renders from the status,
Redis consults the cause first. One classification, two renderers, no lost
fidelity.

**Exit criteria — met.** `resp.rs` has no `metrics` call for a storage command
(what remains is `AUTH`/`HELLO`/`QUIT` and parse failures, none of which reach
the executor); there is exactly one `StoreError → Status` classification; and
all 497 tests, including the full memcached and Redis wire suites, pass
unchanged.

What the bypass costs today, independent of atomicity:

- **Metrics are hand-placed.** `state.metrics.write()` appears at roughly fifteen
  sites in `resp.rs`, against one accounting point at `dispatch.rs:475` that
  every VCP and memcached command passes through. A command returning early
  through a path nobody instrumented is silently uncounted, and the failure is
  invisible — a dashboard that under-reports looks like a quiet server.
- **Error mapping exists twice**, as `to_status` and as `impl From<StoreError>
  for Failure`, and they must agree about which storage failures are the client's
  fault forever.

Not everything moves. `HELLO` negotiates a version that only RESP has, and
`TYPE` answers a question only Redis asks. Those stay dialect-local, and the
distinction is the useful one: **commands that touch storage go through
`Command`; commands that are about the conversation do not.**

Error classification should collapse the same way. `StoreError` is classified
twice today — as `to_status` and as `impl From<StoreError> for Failure` — and the
two have to agree forever about which storage failures are the client's fault.
The fix is the shape memcached already uses: one `StoreError → Status`
classification, then one `Status → wire` renderer per dialect.

**Exit criteria:** every storage-touching RESP command is counted by the same
code that counts the other two dialects; `resp.rs` contains no `metrics` call for
one; one `StoreError → Status` classification and no more.

## Phase 3 — make the `Store` seam real

**Decision: `ServerState.store` becomes `Arc<dyn Store>`.**

The trait's own documentation says it keeps the LMDB decision reversible and
lets the server be tested against an in-memory fake. Neither is true as wired:
there is one implementor and every consumer names `LmdbStore` — `state.rs:11`,
`lib.rs:141`, and nine sites in `cluster.rs`. A libmdbx swap would touch all of
them, and no fake can be substituted.

`dyn` rather than a generic parameter on `ServerState`: the parameter infects
every type that holds one, which is `ServerState`, `Cluster`, both executors and
every test helper, to buy a dispatch that is already dominated by a B-tree
descent. If a benchmark ever disagrees, the change from `dyn` to a parameter is
mechanical and this note is the reason to expect it.

`LmdbStore`-specific methods that are not on the trait — `shard_count`,
`pressure`, `close` — either join the trait or move to construction, where the
concrete type is legitimately known.

**Exit criteria:** an in-memory `Store` implementation exists in test support and
at least one server test runs against it, which is the only proof the seam is
real.

## Phase 4 — split `engine.rs` by concern

**Decision: move each operation next to the layout it acts on.**

`engine.rs` holds environment setup, reads, writes, the sweeper, the evictor, the
tag reclaimer and stats. Meanwhile `expiry.rs`, `tags.rs` and `reclaim.rs` hold
only the *key layouts* those operations use. The split is format-versus-operation,
so every feature spans two files and all the operation halves pile into one.

Rust allows inherent `impl` blocks across modules within a crate, so this is a
move, not a redesign: `sweep`/`evict`/`drain_expiry_index` join `expiry.rs`,
`reclaim_step`/`next_job` join `reclaim.rs`, environment opening becomes `env.rs`.
What remains in `engine.rs` is the record operations and the struct itself.

Deliberately after phases 1–2, which add and delete engine code. Moving first
would mean rebasing the interesting change across a large mechanical diff.

**Exit criteria:** no module in `vash-store` over ~600 lines; no behaviour change;
the test suite is not edited, only re-run.

## Phase 5 — collapse the connection-drain duplication

**Decision: one drain, parameterised by dialect; one definition of "this cannot
write".**

Two related duplications in `conn.rs`:

**`is_read_only` exists three times** — by VCP opcode, by memcached command, by
RESP command — each independently deciding what cannot write. A wrong answer in
any one routes a write onto a runtime worker, where it blocks on the writer queue
and stalls every connection that worker serves. That is precisely the failure the
network/storage split exists to prevent. It only bites with `inline_reads`
enabled, which is why it has not. At minimum a test asserting the three agree for
equivalent operations; better, one predicate derived from the `Command` the
dialects already produce.

**The three `drain_*` functions repeat a stateful pattern** — measure whole
commands, check `inline_reads && all_reads`, clone the connection's auth state,
`spawn_blocking`, copy the mutated state back — and RESP additionally threads the
negotiated version. A fourth dialect means getting the copy-back right a fourth
time, and forgetting it loses an authentication silently rather than loudly.

The re-parse on the blocking thread is not incidental and must survive: it is
what keeps borrowed key and value slices from crossing a task boundary.

**Exit criteria:** one drain function; one read-only predicate, or a test that
proves the three agree.

## Phase 6 — the observability the plan promised

**Decision: add latency histograms split by stage, `oldest_reader_age_ms`, and a
per-command, per-dialect command counter.**

Plan §12 asked for "latency histograms per command, split into queue-wait vs.
execution — the split is what tells you whether the shard writer is the
bottleneck". None of it exists; `metrics.rs` counts reads, writes and other. That
split is exactly the question M6's benchmarking could not answer from the server's
own instruments, and had to answer with external harnesses.

`oldest_reader_age_ms` is listed in plan §15 as the mitigation for a
**High**-impact risk — a long-lived read transaction blocks page reuse and grows
the file without bound. `opcodes.md:814` acknowledges it is unimplemented and
notes M8's listing scans, which hold the longest read transactions the server
opens, finally give it a reason to exist. It is now the oldest outstanding
promise in the plan.

Histograms are hand-rolled fixed-bucket atomics, consistent with `metrics.rs`
rendering Prometheus text directly. A recorder facade would be more machinery
than it saves at this instrumentation count, and the exposition format staying
explicit is what makes the series trustworthy.

**Exit criteria:** queue-wait and execution are separately visible per command;
an alarm can be written for reader age; no counter reports a number it does not
measure.

## Phase 7 — the small ones

- **`ttl_for` takes `now` as a parameter** specifically so a batch stamps every
  key against one instant — and then calls `ttl_from_deadline`, which reads the
  clock again. The stated invariant does not hold. Thread the instant through.
- **`SO_REUSEPORT` and `socket2`** are in plan §2 and were never adopted; there is
  a single accept loop. Either measure a sharded accept path or record the
  decision not to, the way every other deviation in the plan is recorded.
- **Expose arithmetic over VCP.** The native protocol has no arithmetic opcode at
  all, so a first-party client has to fall back to a compatibility dialect to
  increment a counter — the wrong way round. Phase 1 builds the primitive; this
  is the opcode, its codec, its fuzz seeds and its `opcodes.md` contract.

---

## What this milestone will not do

- **Force RESP's connection commands through `Command`.** `HELLO` and `TYPE` are
  Redis's conversation, not the cache's domain.
- **Add multi-key atomicity across shards.** Still a non-goal (plan §16), and
  nothing here changes that.
- **Chase the SET throughput goal.** M6 established the ceiling is the device.
